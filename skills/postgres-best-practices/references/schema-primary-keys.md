# Use BIGINT GENERATED ALWAYS AS IDENTITY for primary keys

## Problem

Choosing the right primary key type affects index fragmentation, storage size, insert performance, and replication behavior. `SERIAL` is legacy PostgreSQL syntax with subtle ownership quirks. Random UUID v4 primary keys cause significant B-tree fragmentation on large tables. `GENERATED ALWAYS AS IDENTITY` is the SQL standard, portable, and preferred for sequential primary keys. UUID v7 (ordered) is appropriate for distributed systems.

## Bad Example

```sql
-- BAD 1: Using SERIAL (legacy — does not use SQL standard syntax)
-- SERIAL is shorthand for INT + a sequence, but with implicit ownership quirks
CREATE TABLE products (
  id SERIAL PRIMARY KEY,   -- INT range: 2.1 billion max → use BIGSERIAL or IDENTITY
  name TEXT NOT NULL
);
-- Problems:
-- 1. SERIAL uses INT (max 2.1B) — silently wraps around on large tables
-- 2. The sequence is created with implicit ownership; ALTER TABLE quirks
-- 3. Not SQL standard (not portable)

-- BAD 2: Random UUID v4 primary key on a large table
CREATE TABLE events (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  event_type TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
-- Problem: Random UUID v4 inserts into random positions in the B-tree index.
-- On a 100M-row table, each INSERT requires a random page write.
-- B-tree fragmentation grows until the index is much larger than the data.
-- Heap storage is also fragmented because rows are not inserted in index order.
```

## Good Example

```sql
-- GOOD 1: BIGINT GENERATED ALWAYS AS IDENTITY (SQL standard, PostgreSQL 10+)
-- This is the recommended approach for sequential primary keys
CREATE TABLE products (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL
);
-- GENERATED ALWAYS AS IDENTITY uses a sequence underneath but is SQL standard.
-- BIGINT range: 9.2 quintillion — effectively infinite for any real table.
-- Identity column cannot be overridden by INSERT unless OVERRIDING SYSTEM VALUE is used.

-- GOOD 2: GENERATED BY DEFAULT AS IDENTITY (allows explicit value override)
CREATE TABLE products_import (
  id   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL
);
-- Allows INSERT INTO products_import (id, name) VALUES (1000, 'Widget')
-- Useful during data migrations where you need to preserve existing IDs.

-- GOOD 3: UUID v7 for distributed systems (ordered UUID)
-- UUID v7 is time-ordered — inserts go to the end of the B-tree (no fragmentation)
-- Available via the uuid_generate_v7() function (requires pg_uuidv7 extension)
-- Or generate in application code (many language libraries support UUID v7)
CREATE TABLE events (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- use v7 UUID from app
  event_type TEXT        NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
-- Application generates UUID v7: uuid7.generate() → time-sorted, no fragmentation

-- GOOD 4: gen_random_uuid() for non-performance-critical tables (PostgreSQL 13+ built-in)
-- Acceptable for small tables, config tables, or tables without high insert rates
CREATE TABLE api_keys (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    BIGINT NOT NULL REFERENCES users(id),
  key_hash   TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

```sql
-- Check sequence status for identity columns:
SELECT sequence_name, last_value, increment_by, max_value
FROM   pg_sequences
WHERE  schemaname = 'public'
ORDER  BY sequence_name;

-- Check if a BIGINT PK is near exhaustion:
SELECT relname, n_live_tup
FROM   pg_stat_user_tables
WHERE  n_live_tup > 1800000000  -- approaching INT limit
ORDER  BY n_live_tup DESC;
```

## Why It Matters

- **INT vs BIGINT exhaustion**: `SERIAL` uses `INT` (max 2,147,483,647 ≈ 2.1 billion). A high-throughput table inserting 1,000 rows/second exhausts INT in ~25 days. `BIGINT` (max 9.2 quintillion) is effectively infinite.
- **Random UUID B-tree fragmentation**: Random UUID v4 inserts scatter new rows throughout the B-tree. Pages cannot be filled sequentially — each insert may require a page split in the middle of the tree. After millions of inserts, the index is 2–3× larger than equivalent sequential-key indexes and slower to scan.
- **Aurora replication**: Aurora PostgreSQL uses the primary key for replication parallelism in some contexts. Sequential primary keys improve replication throughput.
- **`GENERATED ALWAYS` vs `GENERATED BY DEFAULT`**: `ALWAYS` prevents accidental override during application INSERTs. `BY DEFAULT` allows override (useful during migrations). Choose based on whether you ever need to specify explicit ID values.
- **SERIAL ownership quirk**: `DROP TABLE` drops the underlying sequence. But `ALTER TABLE ... SET DEFAULT nextval(...)` can accidentally detach the sequence — `IDENTITY` avoids this entire class of problem.

## Aurora/RDS Notes

- **Aurora PostgreSQL**: Identity columns and sequences are local to the writer node. Read replicas do not have writable sequences. Always insert through the writer endpoint for any query that generates new IDs.
- **RDS PostgreSQL**: Same behavior as community PostgreSQL. No special considerations for identity columns on RDS.
